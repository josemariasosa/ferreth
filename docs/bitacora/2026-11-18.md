## What Ferreth is becoming

Ferreth compiles EVM bytecode into RV64 guest programs. The guest performs arithmetic and stack effects; the host initializes, executes, and observes the guest. The compiler must remain independent of the reference EVM used to evaluate it.

We want a compiler that is robust, understandable, and honest about its guarantees. Research is not a distraction from development: it resolves uncertainty before we commit to architecture. Prefer small experiments, explicit contracts, independent references, focused regressions, and reviewable changes. Do not optimize or generalize before correctness is established.

The repository, not conversations or agent memory, must preserve the project's accumulated knowledge.

### Priority 3.5 — Isolation of conformance

The initial audit established that REVM was not on the compiler-to-RV64 execution path. It supplied U256 via re-export, reference execution APIs (`run_evm*`), tests and benchmarks. We chose to remove the engine from the compiler entirely, using Alloy primitives directly.

Target organization:

```text
crates/ferreth-compiler/       # decoder, codegen, linker, guest execution
crates/ferreth-conformance/    # REVM reference, differential tests, benchmarks
research/eels-cancun/          # independent research
research/revm-frame/           # independent research
```

Conformance depends on compiler and REVM, never the reverse. The compiler CLI owns `translate`, `execute`, `decode`; conformance owns `bench`. Keep executor instrumentation in the compiler. REVM may remain in the shared Cargo.lock; dependency trees, not lockfile presence, determine compiler coupling.

Our manual migration accidentally placed integration tests under `src/tests/` instead of package-root `tests/`. Cargo did not discover them, and green checks concealed the loss of 4,600 differential cases. Independent cross-review detected this. Remediation restored all three integration targets, fixed stale imports, CLI usage, README/runbooks and mechanical ADR paths. This is an important lesson: verify discovery and execution, not just exit status.

## Open thread A — Canonical opcode identity

**Maintainer preference:** one principal EVM `Opcode` identity from which production byte/mnemonic information and subsequent representations derive. This is a design direction, not yet an approved implementation. Avoid a speculative registry or making every representation identical.

The completed source/history audit found that the current `Opcode` is a historical selector for standalone pointer-based ADD/SUB leaf routines, not a complete EVM identity. Both those routines and stack-aware guest wrappers reuse the same arithmetic core. In particular, `generate_guest_add()` calls `Opcode::Add.assembly()` after compiler dispatch has already selected ADD, whereas PUSH1 generates stack-aware assembly directly. The arithmetic implementation belongs in the compiler, not in the oracle layer.

| Current representation | Actual role |
|---|---|
| `Opcode` | ADD/SUB standalone selector, mnemonic, byte, assembly |
| `Instruction` | Simplified decoded stream; PUSH value without original width/offset; legacy ProgramRunner and display |
| `DecodedInstruction` | Executable-prefix decoding, offsets, immediate values and raw PUSH byte |
| `DisassembledInstruction` / `DisassembledKind` | Physical byte spans, static mnemonic table, missing bytes; walks past STOP |
| `CompiledOperation` / `has_explicit_stop` | Backend lowering and supported-operation selection |
| `GeneratedOperation` / `GeneratedRv64` | Generated code and linking metadata |
| Test-only `GeneratedInstruction` | Independent corpus generation and checking |

These are not seven equivalent abstractions. Preserve stage-specific information and independent test encoders. The duplication worth investigating is production opcode identity (bytes, names, immediate widths), not every repeated enum variant.

Proposed direction:

- Establish a canonical identity for at least STOP, ADD, SUB, POP, PUSH1 and DUP1. Decide explicitly how recognized but unsupported PUSH2–PUSH32 and the broader Cancun disassembly vocabulary fit; do not reduce existing decoder/disassembler coverage. Recognition and backend support are distinct.
- Consider a narrower `ArithmeticOpcode` selector for standalone ADD/SUB APIs if needed; do not force unsupported operations into that ABI. Audit caller compatibility before changing the public API.
- Separate identity from architecture-specific generation: a shared arithmetic core can be called directly by the standalone and guest codegen paths rather than having the identity enum choose an assembly implementation.
- Centralize production byte/mnemonic facts where useful. Keep immediate/offset data in decoded instances, and RV64 patch data in generated artifacts.
- Static gas and stack requirements may eventually derive from canonical identity, with a fork-aware contract where needed. Do not add gas semantics before ADR-002 approval.

The agent recommended only renaming the old selector to `ArithmeticOpcode` with a compatibility alias and deferring broader consolidation. This is a valid lower-risk alternative, but the maintainer prefers investigating a canonical identity now. The audit was source-only (at commit `4865e1c`); no tests or benchmarks were executed for that proposal.

Suggested next investigation: map current consumers in `lib.rs`, `compiler.rs`, `disassembler.rs`, `execution.rs`, `orchestrator.rs`, `rv64/opcodes/`, both CLIs and conformance. Propose minimal migration chunks, decide compatibility policy, capture baseline assembly/machine code and metrics, then implement only after review. Verify unchanged bytes, offsets, guest results, benchmark hashes/instruction counts and all workspace suites. Keep this separate from linker changes and gas metering.

## Open thread B — Understand the linkers before changing them

**Maintainer concern:** multiple paths exist and are not yet fully understood. The next session may be dedicated to learning them manually rather than implementing anything.

Observed paths from the audit:

1. Standalone arithmetic leaf execution (`Rv64Runner`): pointer ABI, arithmetic microbenchmarks, no EVM frame gas contract by itself.
2. Isolated stack-aware ADD/SUB guest execution: separate linker around the same guest generators.
3. PUSH1-only sequence linker (`compile_push1_program()`), also reached for empty input and PUSH1-only programs without explicit STOP.
4. Mixed whole-program compiler (`compile_supported_program()`), selecting guest generators and patching exceptional exits.
5. Explicit STOP handled by linker, implicit end-of-bytecode falls into the normal publisher. Isolated POP/DUP1 already reuse bytecode compilation.
6. Legacy host-stack `ProgramRunner`, still used by conformance tests, including wide PUSH programs outside guest backend support. This is a separate execution model, not necessarily another linker.

Known ADD wrapper details: `s0` is the stack base, `s1` is next free slot. Check for two 32-byte words; derive a0/a1/a2; call `evm_add` locally via `jal ra`; retire the top slot; jump over the core/trampoline. `GeneratedRv64LinkMetadata` records the core-call offset, normal continuation offset and exceptional trampoline offset. Underflow is patched by the linker. PUSH1 has an overflow trampoline but no equivalent optional link metadata in the supplied implementation. Investigate how its patch site is determined; do not assume the difference is a bug.

Questions to resolve hands-on:

- Where does each path start and finish? What public APIs and CLI/benchmark commands use it?
- Which parts generate instruction bodies, concatenate code, resolve labels, patch jumps, publish status/exception results, initialize registers, and reach the host exit sentinel?
- Why do ADD/SUB require link metadata but PUSH1/POP/DUP1 currently do not? What assumptions are encoded in fixed offsets?
- Which paths are contractual EVM guests versus isolated microbenchmarks or legacy test helpers?
- Can isolated guest APIs delegate to the whole-program compiler without losing initial-stack support, measurements, or ABI guarantees? Is PUSH1 specialization still useful?
- Are multiple linkers justified, or do they duplicate epilogues, exceptional routing and composition logic? Can one narrow shared linking primitive reduce risk without erasing intentional differences?
- How will every actual guest path satisfy the same gas contract, including explicit STOP and fallthrough? Keep standalone leaf benchmarking separate if appropriate.

Suggested learning session: trace `600260030100` from decoded instructions through lowering, each generated RV64 body, final patch sites and epilogue to guest result. Compare `[0x60, 0x02]`, explicit STOP, an isolated ADD with seeded stack, and an underflow case. Inspect assembly, instruction addresses and register/memory state. Establish which offsets are RV64 byte offsets versus EVM bytecode PCs. Record findings before proposing consolidation.

Do not assume a single linker is automatically better. First understand behavior and ownership. If consolidation is justified, require pre/post guest equivalence, preserve standalone benchmark contracts and accepted ADR-001, and make it a separate reviewed change. Exact generated bytes may legitimately change in a linker refactor; document and explain changes rather than promise byte identity in that case.

## Verification strategy going forward

Three complementary layers:

- **Deterministic compiler tests:** explicit expectations derived from specifications and research. No REVM engine or Python dependency. Protect known behavior and internal guest contracts.
- **Dynamic differential conformance:** separate crate, REVM as a reference, seeded and directed tests. Preserve existing transaction-based comparisons; add frame-equivalent gas comparisons rather than misusing transaction gas. Dynamic verification catches discrepancies without manually calculating thousands of outputs.
- **Independent research:** EELS and REVM runners used on demand to investigate edge cases, arbitrate discrepancies with primary sources and establish new regression requirements. Neither engine is automatically correct on every internal diagnostic. Do not replace all dynamic tests with snapshots of one oracle.

Example research commands:

```sh

cargo run --locked -q -p revm-frame -- --code 5a5a00 --gas 10
```
