## Objective

Specify and implement a synthesizable, combinational arithmetic unit that computes exactly 256-bit addition and subtraction modulo \(2^{256}\). This module is an arithmetic component only; it is not a CPU, EVM interpreter, or complete implementation of Ethereum opcode semantics.

This remains Ferrum ETH's existing standalone RTL and agent-workflow experiment. It does not translate EVM bytecode, test opcode-level behavioral parity or gas accounting, or establish that RTL or agent orchestration offers a performance advantage. The mission's interface, deliverables, verification requirements, and acceptance criteria below remain specific to this RTL component.

## Hardware interface requirements

Implement exactly one top-level module named `eth_alu256` with exactly these ports and no others:

| Port | Direction | Width | Meaning |
|---|---|---:|---|
| `a` | input | 256 bits | First unsigned operand bit vector |
| `b` | input | 256 bits | Second unsigned operand bit vector |
| `op` | input | 1 bit | Operation selector: `0` selects ADD; `1` selects SUB |
| `result` | output | 256 bits | Low 256 bits of the selected operation |

The module is purely combinational: it has no clock, reset, state, request/valid protocol, or handshaking. For every binary input tuple `(a, b, op)`, `result` must be completely defined as a function of the current inputs, without dependence on prior input values. Four-state `X` or `Z` values are outside the input contract.

## Functional semantics

Interpret `a` and `b` as unsigned 256-bit values and define:

- `op == 1'b0`: `result = (a + b) mod 2^256`.
- `op == 1'b1`: `result = (a - b) mod 2^256`.

Overflow and underflow wrap modulo \(2^{256}\). No carry, borrow, or overflow flag is required or permitted as an additional interface output. The implementation must not infer storage or a latch and must provide the defined result for every binary input.

There are no gas, EVM stack, revert, memory, opcode-dispatch, or other EVM execution semantics in this contract. The operand order is exactly as written in the equations above.

## Deliverables

1. `hardware/rtl/eth_alu256.sv`, meeting the exact interface and behavior above.
2. `hardware/sim/tb_eth_alu256.sv`, an automated testbench that checks the DUT against expected values and reports failing operation and operands.
3. `hardware/sim/ref_eth_alu256.py`, an independent software model using arbitrary-precision integer arithmetic, with explicit masking to 256 bits. The model must not derive expected results from the DUT or duplicate its internal RTL implementation.
4. `hardware/sim/eth_alu256_regressions.txt`, the persistent vector corpus. Include all directed cases and every discovered failing input; never delete or replace a failure case to make a run pass.
5. `scripts/test_eth_alu256.sh`, which runs lint, compiles the testbench with Verilator, and runs the full regression without installing dependencies.
6. `hardware/rtl/eth_alu256-design.md`, a concise description of the interface, arithmetic contract, and design choices. Do not prescribe or claim an unmeasured internal implementation property.
7. `hardware/sim/eth_alu256-verification-report.md`, populated with actual observed results, not planned or asserted results.

## Verification requirements

The prescribed command is:

```text
scripts/test_eth_alu256.sh [SEED]
```

`SEED` is an optional unsigned 64-bit integer in decimal or `0x`-prefixed hexadecimal. If omitted, use `0x455448303031`. Use only the Python 3 standard library and Verilator; do not add dependencies. The command must lint the RTL, compile the RTL and testbench, and execute the automated regression. It must return nonzero on any lint, compile, or test failure. Do not suppress Verilator warnings; any warning is a failure unless the mission is explicitly revised and re-approved to document a waiver.

The software reference must independently compute the expected result for each vector as `(a + b) & (2^256 - 1)` or `(a - b) & (2^256 - 1)`, according to `op`. Compare all 256 result bits.

### Required directed coverage

Exercise both operations for at least:

- Zero with zero; zero and one identities (`a + 0`, `0 + b`, `a - 0`); equal operands for subtraction.
- Maximum value `2^256 - 1` with zero and one for addition, including wraparound; maximum minus itself, zero minus maximum, and zero minus one.
- Carry and borrow propagation across every 64-bit boundary. For `k = 1, 2, 3, 4`, test addition of `1` to `2^(64k) - 1` and subtraction of `1` from `2^(64k)`. Include the full-width wraparound cases at `k = 4`.
- Directed values around each 64-bit boundary, including single-bit values at and adjacent to bit positions `64k` for `k = 1, 2, 3`, in operand positions sufficient to exercise both operations.

Each directed case must be checked against the independent reference, with expected and actual values available in failure evidence.

### Deterministic randomized coverage

For each operation independently, run at least 1,000 randomized `(a, b)` pairs. The default seed and any explicitly supplied seed must reproduce the same vectors and order. Use this exact 64-bit SplitMix64 stream to make vector generation reproducible:

1. Initialize `state` to the supplied seed. For each output word, set `state = (state + 0x9E3779B97F4A7C15) mod 2^64`, then set `z = state`; apply, in order, `z = ((z xor (z >> 30)) * 0xBF58476D1CE4E5B9) mod 2^64`, `z = ((z xor (z >> 27)) * 0x94D049BB133111EB) mod 2^64`, and return `z xor (z >> 31)`.
2. Generate ADD vectors first, then SUB vectors. For each of the 1,000 or more pairs in each operation, draw four successive words for `a`, then four for `b`. Word 0 occupies bits `[63:0]`; word 3 occupies bits `[255:192]`.
3. Record the seed, random-case count per operation, generator policy/version, and command in the report. Never rotate or replace a seed after a failure. Preserve every failing `(op, a, b)` as an exact regression vector and retain the original run evidence. Re-run the failure vector as part of the regression after any repair.

### Evidence and reporting

The report must record the mission version, RTL/repository revision, starting commit, Verilator and Python versions, full command and arguments, seed, directed/random counts per operation, lint and compile outcomes, total test outcomes, and any warnings or deviations. Put generated logs and build products under `runs/ETH-001/`. On failure, capture the operation, exact 256-bit hexadecimal operands, expected and actual results when available, seed and case index, command, and relevant log. Preserve failure inputs in the source-controlled regression corpus even after the implementation is repaired. An agent's claim without executed command output and retained evidence does not establish verification.

## Acceptance criteria

The mission passes only if every gate below passes:

1. Every required deliverable exists at its authorized path; the regression corpus may be empty only when no failure has been discovered.
2. The RTL compiles and lints with Verilator using the prescribed script, with zero warnings and no warning suppressions.
3. The compiled top-level module is exactly `eth_alu256` and has only the four specified ports, names, directions, and widths.
4. The design is synthesizable and purely combinational, with no clock, reset, state, inferred latch, or handshaking behavior. RTL must not use simulation-only constructs such as delay controls, `initial` blocks, `force`/`release`, or DPI.
5. Every required directed case, every retained regression vector, and at least 1,000 deterministic randomized pairs per operation execute in the automated regression.
6. Every tested result exactly matches the independent software reference; required tests have a 100% pass rate.
7. The test command exits nonzero for lint, compilation, or test failures, and produces reproducible evidence sufficient to rerun a failure using its exact vector and seed.
8. The verification report contains measured outcomes from an actually executed run. Missing, fabricated, or unexecuted verification evidence is a failure.

Qualitative review cannot override a failed gate. Any missing required artifact, interface mismatch, functional mismatch, failed required test, or unexecuted verification makes the mission fail.

## Explicit non-goals

- FPGA deployment.
